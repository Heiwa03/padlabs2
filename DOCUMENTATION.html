1. What the project does

It is a message broker: a middle program that receives messages from senders and delivers them to receivers, so the two sides never talk to each other directly. A sender only says "publish this message on topic orders"; any receiver that is subscribed to orders gets it.

Part 1 of the assignment built this with raw TCP sockets, where you must invent your own message format and read/write bytes yourself. Part 2 (this project) keeps the same architecture but replaces sockets with RPC (gRPC): instead of sending bytes, programs call functions like Publish(...) that run on another machine. The data format is defined in a .proto file (Protocol Buffers).

One-sentence summary for the teacher: "A C# gRPC broker that routes typed protobuf messages by topic from Python senders to Python receivers, validates input, handles requests concurrently, stores messages durably on disk, and guarantees at-least-once delivery with acknowledgements, retries and a dead-letter topic."

2. Concepts explained simply

2.1 Message broker (agent de mesagerie)

Think of a post office. You do not walk to your friend's house; you drop a letter at the post office with an address (the topic) and the post office delivers it. Benefits:

  • Decoupling: the sender does not know who receives, how many receivers there are, or whether they are online right now.
  • Asynchronous communication: the sender hands over the message and continues; the receiver processes it later, at its own speed.
  • Flexibility: you can add a new receiver without touching the sender.

Costs (from the assignment): the broker is a single point of failure, adds an extra hop (latency), and must be maintained.

2.2 Publisher / Subscriber and topics

A topic is a named channel (like a radio frequency or a YouTube channel). Publishers send to a topic; subscribers listen to topics they care about. Every subscriber of a topic gets its own copy (this is called fan-out). Subscribers of other topics get nothing. The alternative, explicit queues, requires the sender to know a queue name; topics hide the routing behind a logical name.

2.3 Sockets vs RPC

Sockets (Part 1)RPC / gRPC (Part 2)
You writeConnection handling, message framing (where does a message end?), parsing, error codesJust call a function; the library does networking and serialization
ContractWritten in documentation, enforced by your codeWritten in a .proto file, enforced by generated code
TypingText (JSON) you must parse and validate yourselfStrongly typed fields; wrong types are rejected automatically
Abstraction levelLowHigher: you focus on logic, not bytes

RPC = Remote Procedure Call: calling a function that physically runs in another process or machine as if it were local. The client holds a stub (a fake local object); calling stub.Publish(...) serializes the arguments, sends them over the network, the server runs the real method, and the result comes back.

2.4 gRPC

An open-source RPC framework from Google. It uses HTTP/2 as transport (one TCP connection carries many parallel calls, binary framing, built-in streaming) and Protocol Buffers as the data format. It supports four call types:

TypeMeaningUsed here
Unary1 request → 1 responsePublish, Ack
Server streaming1 request → many responses over timeSubscribe (the broker pushes messages)
Client streamingmany requests → 1 responsenot used
Bidirectional streamingboth sides streamnot used

2.5 Protocol Buffers (protobuf)

A schema language plus a compact binary serialization. You describe messages in broker.proto; the compiler (protoc) generates classes for C# and Python from the same file, so both languages agree on the structure. Each field has a number (string topic = 1;) — the number, not the name, goes on the wire, which makes messages small and lets you evolve the schema without breaking old clients. Compared to JSON it is smaller and faster to parse, and the schema is mandatory (JSON is self-describing but unchecked).

2.5b google.protobuf.Any and typed payloads

A broker should not need to know every kind of message that will ever flow through it. Any is a protobuf "envelope inside the envelope": it holds (a) a type URL such as type.googleapis.com/events.OrderCreated and (b) the already-serialized bytes of any protobuf message. The sender calls any.Pack(order); the receiver checks any.Is(OrderCreated) and calls any.Unpack(...) to get a real typed object back. So the data is genuinely protobuf (typed, binary, schema-checked), while the broker's own schema stays small and fixed. The real domain types are in events.proto.

Others you may be asked about: Apache Thrift (similar idea, own RPC + format), Avro (schema stored with the data, popular in Kafka/Hadoop), GraphQL (query language where the client chooses fields; typically over HTTP/JSON, not a message-broker tool).

2.6 Serialization

Turning an in-memory object into bytes/text for sending (and back = deserialization). Here two layers exist: the sender serializes its business object (e.g. OrderCreated) to protobuf bytes and packs it into an Any (the payload), and gRPC serializes the whole request (topic + payload + …) into binary on the wire. The broker never rewrites the payload; it validates it and forwards the same type URL and bytes.

2.7 Concurrency, threads, thread-safe collections

Concurrency means handling several things at once so that one slow request does not block others. With sockets you would do thread-per-request manually. Here, ASP.NET's server (Kestrel) automatically runs each incoming gRPC call on a thread-pool thread, and async/await frees the thread while waiting for I/O. A race condition happens when two threads modify shared data at once and corrupt it; thread-safe collections (ConcurrentDictionary, Channel<T>) are built to be used from many threads without explicit locks. Where a lock is needed (writing the file) I use SemaphoreSlim.

2.8 Background worker / cron job

A loop that wakes up on a timer and does work independent of any request. Here DispatchWorker wakes every 200 ms, looks at stored messages and pushes them to subscribers. This separates receiving (fast, in the request) from delivering (done by the worker), which is what the assignment calls "work jobs".

2.9 Transient vs persistent storage

  • Transient: only in memory. Fast but lost if the broker stops.
  • Persistent: also written to disk. Survives a crash.

This project does both: memory (ConcurrentDictionary) for speed, mirrored to store.jsonl on disk (one base64-encoded protobuf Message per line) for durability.

2.10 Delivery guarantees

GuaranteeMeaningProblem
At-most-oncesend once, never retrymay lose messages
At-least-once (ours)retry until acknowledgedmay deliver duplicates
Exactly-onceonce and only oncevery hard in distributed systems

ACK (acknowledgement): the receiver says "I processed message X". If no ACK comes within AckTimeoutMs, the broker resends. After MaxAttempts failures the message is moved to the dead-letter queue ($dlq topic) so it does not retry forever and a human/another program can inspect it. Because duplicates are possible, receivers should be idempotent (processing the same message twice has no extra effect).

2.11 Deduplication and idempotency

A sender may retry a publish after a network error and accidentally send twice. If it gives the message an id, the broker recognizes a repeated id and answers duplicate=true without storing it again.

2.12 Why TCP / HTTP/2 (and not UDP)

TCP is reliable (retransmits lost packets, keeps order, detects broken connections). UDP is faster but may lose, duplicate or reorder packets. A broker must not lose messages, so TCP is the right choice. gRPC runs on HTTP/2 which runs on TCP, so this is automatic.

3. Architecture

Three kinds of process: sender (producer), broker (middle) and receivers (consumers). Communication is logically unidirectional: sender → broker (Publish) and broker → receiver (stream opened by Subscribe). The only reverse traffic is the small Ack call.

4. The gRPC contract (broker.proto)

service MessageBroker {
  rpc Publish   (PublishRequest)   returns (PublishReply);        // sender -> broker
  rpc Subscribe (SubscribeRequest) returns (stream Message);      // broker -> receiver (push)
  rpc Ack       (AckRequest)       returns (PublishReply);        // receiver -> broker
}
MessageFieldsPurpose
PublishRequesttopic, payload (google.protobuf.Any), sender, id (optional)what the sender submits
PublishReplyok, error, message_id, duplicate"accepted" or "rejected because…"
SubscribeRequesttopic, subscriber (logical name)"send me everything for this topic"
Messageid, topic, payload, sender, timestamp_msone delivered message
AckRequestsubscriber, message_id"I processed this one"

Data representation required by the assignment: proto, end to end. The business data is a typed protobuf message, carried in an Any so the broker forwards it unchanged (the assignment says the message must not be altered in transit).

The domain schema (events.proto)

message OrderCreated { int64 order_id = 1; string customer = 2; double total = 3; }
message Notification {
  enum Severity { SEVERITY_UNSPECIFIED = 0; INFO = 1; WARNING = 2; ERROR = 3; }
  string title = 1; string body = 2; Severity severity = 3;
}

Both sides compile this file. A new message type = add it to events.proto, regenerate the stubs, and add a rule to PayloadValidator.

Why Any and not a oneof or a generic JSON string?
  • JSON string (my first version): works, but the schema does not describe the data, I had to hand-validate syntax, and it defeats the point of using protobuf.
  • oneof of concrete types: strongest typing, but the broker's own contract must list every message type and change whenever one is added.
  • Any (chosen): typed and binary like the others, while broker.proto never changes when new event types are added. The price: the broker only knows the types it has compiled in, so it rejects anything else.

5. The broker, class by class (Broker/Core.cs)

MessageStore – storage

  • Holds all pending (not yet fully acknowledged) messages in a ConcurrentDictionary<id, Message> → thread-safe, transient part.
  • On every add/remove it rewrites store.jsonl → persistent part. Each line is one protobuf Message serialized to bytes and base64-encoded (the file stays line-based text but holds exactly what the contract defines). It writes to a .tmp file and then renames, so a crash in the middle never leaves a half-written file (the rename is atomic); the rename is retried briefly because Windows can lock the target for a moment. A SemaphoreSlim lock allows only one writer at a time, and group commit lets writers queued behind it share one flush: a caller returns only after a flush that includes its change, but ten concurrent publishes do not cause ten file rewrites.
  • The constructor reloads the file at startup → crash recovery. Corrupt lines are skipped with a warning.

TopicRegistry – routing

  • Maps topic → { subscriberName → Subscriber }.
  • Each Subscriber owns a Channel<Message>: a thread-safe queue where the worker writes and the gRPC stream reads. It also tracks per-message delivery state (attempts, last send time, acked, dead).
  • If a subscriber with the same name reconnects, the old one is replaced (its channel closed).

DispatchWorker – the periodic job

Every DispatchIntervalMs (200 ms) it loops over pending messages and, for each current subscriber of the message's topic:

  1. skip if already acked or dead;
  2. skip if sent recently and the ACK timeout has not expired;
  3. if attempts ≥ MaxAttempts → mark dead and copy the message to topic $dlq;
  4. otherwise increment attempts, record the time, and write the message into the subscriber's channel.

When every subscriber has acked (or is dead) the message is deleted from the store. If there are no subscribers, nothing happens and the message waits → this is the backlog behaviour. The tick is wrapped in try/catch so an error never kills the worker.

BrokerService – the gRPC endpoints

MethodWhat it does
PublishValidates (see below), assigns an id (or uses the client's), checks duplicates, stores the message, replies ok=true. It does not deliver — it only stores, which keeps it fast.
SubscribeRegisters the subscriber, then loops await foreach over its channel writing each message to the gRPC stream. The call stays open until the client disconnects (cancellation token), then it unregisters in finally.
AckMarks the message as acked for that subscriber; the worker then cleans it up.

Validation rules (in Publish)

  • topic required; only letters, digits, . - _; max 100 chars (so $dlq is reserved — nobody can publish into it);
  • payload required, ≤ MaxPayloadBytes (64 KB), with a known type URL; the Any is then unpacked with the generated class (PayloadValidator), which fails on corrupt bytes, and field rules are checked: OrderCreated.order_id > 0, customer required, total ≥ 0; Notification.title required, severity not UNSPECIFIED;
  • id ≤ 128 chars.

Invalid input returns ok=false with an error text; the exception is caught, logged and the broker keeps running. That answers the assignment's "handle exceptions for invalid messages so the broker does not crash".

6. The Python clients

sender.py

Builds a typed message (events_pb2.OrderCreated or Notification), packs it into an Any (the sender serializes), opens a channel to localhost:5000, calls stub.Publish(...) with a 5-second deadline and prints OK id=… or REJECTED: reason. If the broker is down, it catches grpc.RpcError and prints "broker unavailable". --type notification picks the other message type and --invalid sends a message that breaks the field rules (e.g. order_id = 0) to demonstrate rejection.

receiver.py

Calls stub.Subscribe(...) which returns an iterator; for msg in ... blocks and yields messages as the broker pushes them. Each message is handed to a ThreadPoolExecutor (8 workers) so a slow message does not block the stream (concurrent processing). The handler looks up the generated class from the Any type URL, unpacks it into a real typed object, prints its fields and sends Ack; an unknown type is skipped (but still acked so it is not retried forever). A while True loop reconnects after 2 s if the broker disappears.

7. Life of a message

  1. Sender builds OrderCreated(order_id=1, ...), packs it into an Any and calls Publish(topic="orders", payload=...).
  2. gRPC/protobuf turns the request into binary and sends it over HTTP/2.
  3. Broker.Publish validates, creates a Message with a GUID id, saves it to memory and to store.jsonl, replies ok. The sender is now free.
  4. DispatchWorker (≤200 ms later) sees the message, finds subscribers of orders, writes it to each one's channel (attempt 1).
  5. Subscribe stream of each receiver pulls from the channel and sends it down the open connection.
  6. Receiver processes it and calls Ack.
  7. When all subscribers acked, the worker deletes the message from memory and disk.
Failure paths. No ACK → resend every 3 s, max 3 attempts, then copy to $dlq. No subscriber → message stays stored. Broker crash → unacked messages reload from store.jsonl. Receiver crash → its stream ends; on reconnect it gets a fresh state and pending messages are re-sent.

9. Design decisions and why

DecisionReason
gRPC (not Thrift)very widely used, great .NET + Python support, built-in streaming (perfect for push delivery), HTTP/2.
C# for the broker, Python for clientsMixed stack allowed; C# has excellent concurrent collections and background services; Python is quick for small clients; the shared .proto shows that languages are interchangeable behind the contract.
Server streaming for SubscribePush instead of polling: receivers do not hammer the broker asking "anything new?" — the assignment's "message pooling puts pressure on the broker" problem.
Topics instead of explicit queuesThe sender stays unaware of receivers; routing is transparent.
Typed payload in Anyreal protobuf data with schema validation, while the broker contract stays fixed and the bytes are forwarded unaltered. See the comparison in section 4.
Publish only stores; worker deliversfast acknowledgement to the sender, and the delivery logic (retry, backoff, DLQ) lives in one place.
At-least-onceNever lose a message after ok; duplicates are manageable with ids.
Line-based file with atomic renameSimple, crash-safe, no database required; base64 lines keep the exact protobuf bytes.

10. How to run it locally

Requirements: .NET 8 SDK and Python 3 with pip install grpcio grpcio-tools. Three terminals:

# terminal 1 - broker (listens on http://localhost:5000)
cd part2/Broker
dotnet run

# terminal 2 - receiver subscribed to topic "orders" with name "r1"
cd part2/clients
python receiver.py orders r1

# terminal 3 - send 3 messages
cd part2/clients
python sender.py orders 3
python sender.py alerts 1 --type notification
python sender.py orders 1 --invalid          # order_id = 0 -> rejected by validation

Demo ideas for the teacher: (a) start the sender before the receiver — messages are waiting and arrive when the receiver connects; (b) start two receivers with different names — both get each message; (c) stop the broker (Ctrl+C) with messages unacked, restart, and see them delivered; (d) check Broker/store.jsonl while messages are pending.

Regenerate the Python stubs after changing a proto (from part2; the C# side regenerates on build):

python -m grpc_tools.protoc -Iprotos --python_out=clients --grpc_python_out=clients protos/broker.proto protos/events.proto

(events_pb2_grpc.py is generated empty because events.proto defines no service; delete it, it is not needed and not committed.)

Settings are in Broker/appsettings.json: AckTimeoutMs (3000), MaxAttempts (3), DispatchIntervalMs (200), MaxPayloadBytes (65536), StorePath.

12. Limitations (say them before the teacher finds them)

  • Single broker: single point of failure; no replication/standby (the assignment lists the mitigation but does not require it).
  • No consumer groups: every subscriber gets every message (fan-out). Load-balancing among several workers of one logical service is not implemented.
  • Whole-file rewrite on each flush: simple and safe but O(n) (group commit reduces how often); a real broker would append to a log (write-ahead log) and compact periodically.
  • The broker only accepts message types compiled into it (PayloadValidator); a new type means editing events.proto, the validator and rebuilding.
  • Deduplication only while a message is pending: once it is fully acked and deleted, its id is forgotten.
  • At-least-once, not exactly-once: duplicates are possible after timeouts/reconnects; receivers should be idempotent.
  • No security: plain HTTP/2 without TLS, no authentication; fine for a local lab, not for production.
  • The per-subscriber delivery state is in memory: after a broker restart the attempt counters start again (the messages themselves are not lost).
  • A message that lands in $dlq with nobody subscribed to $dlq stays in storage.

13. Questions the teacher may ask

What is the difference between Part 1 and Part 2?

Architecture is identical (sender → broker → receiver, topics, storage, concurrency). In Part 1 I implemented the communication myself on sockets: framing, parsing, threads. In Part 2 gRPC provides connection handling, serialization and typed contracts, so the code deals only with broker logic.

What is Any and why do you use it?

It is a protobuf wrapper holding a type URL plus serialized bytes of any message. It lets the broker carry different typed messages (orders, notifications) without its own contract changing. The sender packs, the broker validates by unpacking with the known type, and the receiver unpacks to a typed object. The bytes are forwarded unchanged.

Why did you change from JSON payloads to typed messages?

The JSON string worked but was not the gRPC way: the schema did not describe the data and I validated syntax by hand. With typed messages the contract documents the data, the generated classes enforce structure in both languages, and validation is about meaning (field rules), not parsing.

Why gRPC and not REST?

gRPC has a strict typed contract, binary encoding (smaller/faster), HTTP/2 multiplexing and native streaming. Streaming matters here: the broker can push messages instead of receivers polling. REST has no natural server-push.

Why protobuf and not JSON?

Smaller on the wire, faster to parse, schema-enforced, code generation for any language. JSON is easier to read and debug but nothing checks its structure. The first version of this project carried JSON text inside the protobuf envelope; I changed it so the payload is a typed protobuf message too (inside Any).

Why TCP and not UDP?

A broker must not lose or reorder messages. TCP guarantees delivery and order; UDP does not. gRPC needs HTTP/2, which needs TCP anyway.

How do you handle concurrency?

The server processes each gRPC call on its own thread-pool task (async, non-blocking I/O). Shared state uses thread-safe types: ConcurrentDictionary, Channel; file writes are serialized with a semaphore. A background worker delivers messages, and the receiver processes messages in a thread pool. Test 09 sends 400 messages from 8 threads and all arrive.

What happens if the broker crashes?

Every accepted message is on disk (store.jsonl) before the sender gets ok. On restart the store reloads it and the worker delivers it as soon as there is a subscriber (test "zz"). Clients catch the connection error; the receiver reconnects automatically every 2 s.

What happens if a receiver crashes or is slow?

No ACK arrives, so after 3 s the broker resends; after 3 attempts the message goes to $dlq. If the receiver disconnects and returns, it re-subscribes and unfinished messages are redelivered.

Can a message be lost? Can it be duplicated?

Not lost after the broker said ok (it is on disk until acked). It can be duplicated (at-least-once): e.g. receiver processed it but crashed before the ACK. Hence idempotent receivers and ids.

How does the broker know where to send a message?

By topic. The sender gives only a topic name; the TopicRegistry knows which subscribers registered for it through Subscribe.

How does the stream (Subscribe) work?

The receiver makes one call and the server never "finishes" it: the server keeps the response stream open and writes a new Message whenever the subscriber's channel has one. The call ends when the client cancels or disconnects; the finally block then unregisters the subscriber.

What is a Channel<T> and why use it?

A thread-safe producer/consumer queue from .NET. The worker (producer) writes, the stream handler (consumer) awaits reads without blocking a thread. It avoids manual locks and busy waiting.

What is a dead-letter queue?

A special place for messages that could not be delivered after the maximum attempts. Without it, a "poison" message would be retried forever. Here it is the reserved topic $dlq; anyone can subscribe to inspect failures.

How does validation work and why is it needed?

The broker is a shared service: one bad message must not crash it or poison receivers. It checks topic characters, payload size, that the type is known, that the bytes decode as that type, the field rules and the id length, and replies with a clear error. Wrong wire types are already rejected by protobuf parsing; the field rules (e.g. order_id > 0) are business validation on top.

Why does Publish not deliver directly?

Separation of concerns and speed: Publish only validates and persists, so senders are not slowed by receivers. The worker handles retries and timing for all messages uniformly.

What would you improve with more time?

Consumer groups for load balancing, a write-ahead log instead of rewriting the file, a standby broker with replication, TLS and authentication, persistent dedup ids, and metrics (queue length, delivery latency).

What is the "single point of failure" and how would you fix it?

If the broker stops, nothing flows. Fix: run a second broker and replicate state to it (primary/standby), with clients failing over. Not implemented here; my disk persistence at least prevents data loss.

Explain the code path of one publish in 20 seconds.

"Sender calls Publish through the generated stub → protobuf over HTTP/2 → BrokerService.Publish validates, stores in memory and file, returns ok → the worker pushes the message into each subscriber's channel → the Subscribe stream sends it to the receiver → the receiver calls Ack → the message is deleted."
